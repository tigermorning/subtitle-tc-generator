## 1. 해결하려는 문제

### 누가 불편한가
- **자막 작가를 준비하는 사람과 막 일을 시작한 프리랜서** — 신청자 본인이 그 당사자입니다.
- 방송·OTT 자막은 보통 여러 역할이 나눠 맡습니다.
  - **TC(타임코드) 작업자**: 말소리를 화면 단위로 끊고 인점·아웃점을 찍음
  - **자막 작업자**: 그 화면 안에 들어갈 글(받아쓰기·번역)을 씀
  - **검수자**: 발주처 규정 위반과 표기 오류를 잡음
- 신입은 이 일을 혼자 다 해야 하는데, 기성 작가가 가진 **속도**와 **"감"**(어디서 끊고, 어디서 줄이고, 무엇을 의심할지)이 없습니다.

### 언제 불편한가
자막 작업을 연습하며 직접 겪은 시간 낭비입니다.

1. **인점·아웃점 찍기**
   - 파형을 보며 한 줄씩 손으로 찍고, 화면 전환에 걸리는지 다시 확인합니다.
   - 기성 작가는 감으로 바로 찍는 자리를, 신입은 몇 번씩 되돌려 듣습니다.
2. **글자 수·읽기 속도 맞추기**
   - 발주처마다 규정이 다릅니다. 예: 넷플릭스 한국어는 **줄당 16자·최대 2줄**, 읽기 속도 **번역 자막 12자/초, SDH 14자/초**(저장소 `rules/learned/netflix/ko-*.yaml` 머리말). 줄당 14자로 조이는 발주처도 있습니다.
   - 규정을 넘긴 줄을 찾아 뜻을 살려 줄이는 일을 줄마다 되풀이합니다.
   - 범용 LLM에 맡기면 규정을 모르고 문장을 늘여 써서 다시 손봐야 합니다.
3. **고유명사 확인**
   - 인명·브랜드·작품명 표기를 하나하나 검색해 확인합니다. 범용 LLM은 표기를 지어내기도 합니다.

### 왜 에이전트인가
- 기성 작가의 "감" 가운데 상당 부분은 **발주처 규정과 업계 관행**입니다(인점은 말소리보다 조금 앞, 아웃점은 말끝보다 조금 뒤, 화면 전환 근처는 피하기 등).
- 규정은 공개된 스타일 가이드에, 관행은 실제로 방영된 자막의 타이밍과 글자 수에 남아 있습니다. 이걸 규칙 파일로 옮기면, 신입도 기성 작가와 같은 기준으로 첫 결과물을 낼 수 있습니다.
- 목표는 **자막을 사람 없이 끝내는 것이 아니라**, 사람이 여럿 붙던 반복 작업을 에이전트가 먼저 처리하고, 신입 혼자서 판단이 필요한 곳만 확인하게 하는 것입니다.

## 2. 에이전트 구조

현업 작업 순서를 그대로 따릅니다. **TC를 먼저 잡아 확정하고 잠근 뒤**, 그 틀 안에서 자막 문장을 만들고 고칩니다.

- **A. TC 작업** — 전사 없이 소리만 보고 인점·아웃점을 잡아 확정·잠금 (TC 작업자 몫)
- **B. 자막 작업** — 잠긴 TC 안에서 전사·번역·줄바꿈을 하고, **판정(Judge) → 교정(Refine)을 되풀이하는 자가교정 루프**로 다듬음 (자막 작업자·검수자 몫)

역할 나눔:
- **숫자로 판정할 수 있는 것(인·아웃점, 글자 수, CPS)은 규칙 코드**가 맡습니다. LLM이 "대충 맞다"고 넘기지 않습니다.
- **Liner Model API는 문장 압축·의역**만 맡습니다. TC는 건드리지 않습니다.
- **Liner Search API·MCP는 고유명사 표기 확인**만 맡습니다.

### A. TC 작업 — 인점·아웃점을 잡는 법

기성 작가가 파형을 보며 감으로 찍던 인·아웃점을, 소리 신호와 발주처 규정으로 계산합니다.

```
[영상/오디오]
       ↓
[A-1: 말소리 구간 검출]
  - 전사 없이 오디오만으로 말소리가 시작·끝나는 경계를 찾음 (Silero VAD)
  - 배경음악·효과음이 큰 장면은 대사 성분을 먼저 분리해 경계를 또렷하게 함
       ↓
[A-2: 발주처 규정 여유 적용 (규칙 코드)]
  - 인점: 말소리 시작보다 2~3프레임 앞
  - 아웃점: 말끝보다 6~9프레임 뒤
  - 앞 자막 아웃점과 다음 자막 인점이 겹치면 인점 우선
  - 최소·최대 표시 시간 지키기
  - 여유값은 코드에 박지 않고 발주처 규정 파일에서 읽음
       ↓
[A-3: 화면 전환 (SDH 작업만)]
  - 화면 전환을 검출해, 전환 앞뒤 0.5초 안에 걸친 인·아웃점을 전환 지점에 맞춤
  - 우선순위: 인점 > 화면 전환 > 아웃점
       ↓
[A-4: 자동 확정과 잠금]
  - 말소리 경계 + 규정 여유와의 오차가 0.04초 미만(1프레임 안팎)이라고 판정된 구간만 자동 확정
  - 확신이 낮은 구간은 "사람 확인" 카드로 넘김 (파형 위치·이유 표시)
  - 확정한 TC는 잠금 — 이후 단계는 TC를 움직이지 않음
```

### B. 자막 작업 — 자가교정 루프

```
[잠긴 TC + (있으면) 원어 대본]
       ↓ 전사(faster-whisper) → 대본 대조 → 번역(번역 작업만) → 줄바꿈
[B-1: 판정 (규칙 코드, 결정론적)]
  - 차원 1: 글자 수 (줄당 상한·줄 수, 발주처 규정 파일 값)
  - 차원 2: 읽기 속도 (잠긴 TC의 표시 시간 대비 CPS 상한)
  - 차원 3: 고유명사 후보 표시 (검증이 필요한 낱말만 골라냄)
       ↓
       ├─ [위반 0건] ──→ [최종 SRT/VTT 출력]
       └─ [위반 있음]
              ↓
[B-2: 고유명사 확인 (Liner Search API·MCP)]
  - 차원 3이 고른 낱말만 검색해 공식 표기를 출처와 함께 확인
              ↓
[B-3: 교정 (Liner Model API)]
  - 위반한 자막의 문장만 뜻을 살려 압축·의역 (TC는 그대로)
  - 판정 결과(어느 규칙을 몇 자 넘겼는지)와 확인한 표기를 함께 넘김
              ↓
[B-1로 돌아가 다시 판정 — 최대 3회]
  - 3회 뒤에도 남은 위반은 억지로 고치지 않고 "사람 확인" 카드로 넘김
    (위반 규칙 ID·자막 번호·이유 표시)
```

TC가 잠겨 있으므로, 읽기 속도를 넘기면 **TC를 늘리지 않고 문장을 줄여서** 맞춥니다. 기성 작가가 하는 방식 그대로입니다.

## 3. 라이너 API 접목 방안

- **Liner Model API — 교정(B-3)의 두뇌**
  - 규정 위반 자막을 뜻을 살려 줄이는 일을 맡깁니다.
  - OpenAI·Anthropic SDK와 호환되므로, 기존 코드에서 주소와 키만 바꿔 연결합니다.
  - 판정은 규칙 코드가 하므로, 모델이 고친 문장도 매번 다시 숫자로 검사받습니다.
- **Liner Search API·MCP — 고유명사 확인(B-2)**
  - 에이전트 루프에 라이너 원격 MCP 서버를 도구로 등록합니다.
  - 고유명사 후보가 나오면 `search_web`(출처 직접 확인)이나 `search_agent`(출처를 단 요약)로 공식 표기를 확인하고, 출처 URL을 판정 기록에 남깁니다.
  - 확인한 표기는 작품별 용어집에 쌓아, 같은 낱말은 다시 검색하지 않습니다.
- **원고 보호 선택지**
  - 대회 시연은 공개 데이터로만 하므로 Liner Model API를 씁니다(아래 4절).
  - 실제 의뢰 원고를 다룰 때는 교정 모델을 로컬 모델로 바꿀 수 있게 설정으로 둡니다. 이때도 라이너 검색에는 대사 문장이 아니라 고유명사 낱말만 보냅니다.

## 4. 시연 데이터와 측정 계획

### 시연 데이터 (참가 규정 제5조 준수)
- 회사 내부 자료·의뢰받은 원고·납품 자막은 쓰지 않습니다.
- **저작권 문제가 없는 공개 영상**을 쓰고, 그 영상의 정답 자막은 **신청자가 직접 만들어** 함께 공개합니다.
- 규정값은 공개된 발주처 스타일 가이드에서 가져옵니다.

### 측정 계획
효과를 숫자로 미리 약속하지 않고, 결과물 제출(11/25)까지 아래 항목을 재서 보고합니다.

| 지표 | 재는 법 |
|---|---|
| 인점·아웃점 정확도 | 직접 만든 정답 자막과 비교해, 인점·아웃점이 1프레임(0.04초) 안에 든 비율과 자동 확정 비율 |
| 규정 위반 감소 | 같은 영상에서 범용 LLM 초안과 에이전트 결과의 위반 건수(글자 수·CPS) 비교 |
| 고유명사 표기 정확도 | 고유명사 목록을 정답 표기와 대조 — 라이너 연동 전과 후 |
| 사람 손이 가는 자막 수 | 최종본에서 "사람 확인" 카드로 남은 자막 비율 |
| 작업 시간 | 같은 구간을 신청자가 손으로 할 때와 에이전트를 거친 뒤 확인만 할 때의 시간 비교 |

## 5. 기대 효과와 확장성

1. **신입 혼자서 여러 사람 몫**: TC 작업자·자막 작업자·검수자가 나눠 하던 반복 작업을 에이전트가 먼저 처리하고, 신입은 "사람 확인" 카드로 추려진 곳만 판단합니다.
2. **기성 작가의 "감"을 따라잡는 학습 도구**: 카드마다 어느 규칙에 왜 걸렸는지 보여 주므로, 쓰면서 규정과 관행을 몸에 익힐 수 있습니다.
3. **SDH 자막 품질 균일화**: 효과음 표기([문이 쾅 닫힌다], [비장한 음악])와 읽기 속도 규정을 매번 같은 기준으로 검사해, 청각장애인 시청자가 받는 자막 품질의 편차를 줄입니다.
4. **다른 발주처·언어로 확장**: 규정은 코드가 아니라 발주처별 규정 파일에 있으므로, 파일을 더하면 다른 발주처와 다른 언어 자막에도 같은 에이전트를 쓸 수 있습니다.

## 6. [11/11 접수용] 온라인 신청서 제출 텍스트 요약

```text
[프로젝트명]
신입 자막 작가가 혼자서 여러 사람 몫을 해내게 하는 SDH 자막 자가교정 AI 에이전트

[해결하려는 업무 문제]
방송·OTT 자막은 보통 타임코드 작업자, 자막 작업자, 검수자가 나눠 맡습니다. 자막 작가를 준비하며 직접 해 보니, 신입은 이 일을 혼자 다 해야 하는데 기성 작가의 속도와 "감"이 없어 시간 낭비가 컸습니다. 인점·아웃점을 몇 번씩 되돌려 들으며 찍고, 발주처마다 다른 글자 수·읽기 속도 규정(예: 넷플릭스 한국어 16자·2줄, 번역 12자/초·SDH 14자/초)을 넘긴 줄을 찾아 줄이고, 고유명사 표기를 하나하나 검색해야 합니다. 범용 LLM은 이 규정을 모르고 문장을 늘여 써서 다시 손봐야 합니다.

[에이전트 작동 방식]
먼저 현업 순서대로 타임코드를 잡습니다. 전사 없이 오디오의 말소리 경계를 찾고, 발주처 규정 여유(인점은 말소리 2~3프레임 앞, 아웃점은 말끝 6~9프레임 뒤, 겹치면 인점 우선, SDH는 화면 전환 앞뒤 0.5초)를 적용합니다. 오차 0.04초 미만으로 판정된 구간만 자동 확정해 잠그고, 나머지는 사람이 확인합니다. 그다음 잠긴 타임코드 안에서 자막을 만들고, 규칙 코드가 글자 수·읽기 속도·고유명사를 판정합니다. 고유명사는 라이너 서치 API·MCP로 공식 표기를 출처와 함께 확인하고, 위반한 자막만 라이너 모델 API가 타임코드는 그대로 둔 채 뜻을 살려 압축합니다. 다시 판정해 통과할 때까지 최대 3회 되풀이하고, 남은 문제는 사람 확인으로 넘깁니다.

[기대 효과]
여러 사람이 붙던 반복 작업을 에이전트가 먼저 처리해, 신입 한 사람이 판단이 필요한 곳만 확인하면 됩니다. 걸린 이유를 매번 보여 주므로 기성 작가의 감을 익히는 도구도 됩니다. 규정을 파일로 두어 다른 발주처·언어로 넓힐 수 있고, 효과는 공개 영상으로 인점·아웃점 정확도·위반 건수·작업 시간을 재서 결과물과 함께 보고합니다.
```
