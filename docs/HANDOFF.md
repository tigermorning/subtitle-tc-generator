# 엔지니어링 핸드오프 — 팀 합류자를 위한 문서

이 문서는 `docs/BACKLOG.md`(날짜순 작업 기록)를 대신하지 않는다. 여기는 **"왜
이렇게 만들었는가"와 "지금 무엇이 비어 있는가"만** 담는다. 과정을 시간순으로
쫓고 싶으면 `BACKLOG.md`를, 작업 규칙 자체를 보려면 `CLAUDE.md`를 본다.

**살아있는 문서다.** 결정이 바뀌거나 새 모델을 들이거나 오래된 미해결 항목이
풀리면 이 파일을 그때그때 고친다. 날짜 붙은 회의록이 아니라 **지금 상태의
지도**로 유지한다 — 오래된 항목은 지우거나 고치지, "2026-08-27에는 이랬음"
식으로 쌓아두지 않는다(그건 BACKLOG.md의 역할이다).

## 1. 무엇을 만드는가

방송·OTT용 자막(TC + SDH + 번역)을 사람 작업자 수준으로 초벌 생성하는 도구다.
납품 대상은 발주처(넷플릭스 등)마다 다른 정식 스타일 가이드를 따라야 하고,
결과물은 항상 **사람이 검수·수정하는 초안**이다 — 완전 자동화가 목표가
아니다(아래 4번 "설계 철학" 참고).

두 축이 있다.
- **TC(타임코드) 작업자**: 말소리를 화면 단위로 끊고 인점·아웃점을 맞춘다.
- **자막(SDH·번역) 작업자**: 그 화면 안에 들어갈 텍스트를 쓴다(원어 그대로
  받아쓰거나, 다른 언어로 옮긴다).

이 도구는 두 역할을 **하나의 파이프라인**으로 자동화하고, 발주처 규정 검사기
(`checker/`)로 사람이 볼 것만 추려낸다.

## 2. 파이프라인 — 순서가 설계의 전부다

```
①전사 -> ②대조(대본 있으면) -> ③번역 -> ④재분할 -> ⑤글자수·스포팅 규정
transcribe.py  align.py          translate.py  resplit.py  timing.py / checks.py
```

이 순서를 바꾸면 결과가 구조적으로 나빠진다(`CLAUDE.md` 규칙 1).

- **전사가 글자 수를 무시하는 이유**: whisper의 `max_len`으로 자르면 문장이
  중간에 끊긴 채 굳는다. 사람도 먼저 다 받아쓰고 나중에 나눈다.
- **재분할이 번역 뒤에 오는 이유**: 원어 기준으로 미리 끊으면 번역문(특히
  한국어)이 그 경계에 갇힌다. 언어마다 문장 구조가 달라 끊는 자리도 달라야
  한다.
- **글자 수가 맨 끝인 이유**: 발주처 규정(줄당 글자 수·읽기 속도)은 **번역문
  기준**이다. 원어 스크립트에 규정을 대는 것은 시간 낭비다.

## 3. 규정(rule) 3계층

```
rules/<플랫폼>/        공식 문건에서 옮긴 값. source.official: true
rules/learned/<플랫폼>/ 정답 자막에서 관측한 값. source.origin: learned
코드 기본값             위 둘 다 없을 때만
```

**학습값이 규정을 덮어쓰지 않는다.** 배운 값이 `rules/<플랫폼>/`를 고치는
일은 없다 — 관측이 공식 문건과 다르면 그건 승격이 아니라 "지적"으로 남긴다.
규정으로 승격하는 유일한 길은 사람이 확인하는 것이다(`CLAUDE.md` 규칙 11).

**`rules/genre/`가 플랫폼 규정 위에 얹힌다.** 예능·다큐처럼 장르가 요구하는
값(예: 병합 상한 2초)은 플랫폼과 별개 계층이다.

**`--lock-timecodes`**: 이미 TC 작업이 끝난 파일에 번역만 붙이는 실무 사례를
위한 모드. 재분할·스포팅을 전부 막고, `--fix-timing`과 같이 쓰면 오류를 낸다
(조용히 무시하지 않는다 — `CLAUDE.md` 규칙 8).

## 4. 설계 철학 — 세 가지가 반복해서 나온다

1. **어느 쪽도 정답으로 두지 않는다.** 전사와 스크립트가 다르면 기계가
   판정하지 않고 표시만 한다. 표기 통일표를 어겨도 고치지 않고 표시한다 —
   문맥상 예외가 실제로 있다.
2. **확실한 근거와 추정을 구분한다.** 파일 안에서 검증 가능한 것(글자 수,
   중복 등)은 자동 교정한다. 영상에서 추정한 것(말소리 구간, 화자 분리,
   화면 캡션 위치)은 **제안만 하고 자동으로 고치지 않는다** — 틀렸을 때
   원인을 사람이 못 찾기 때문이다.
3. **원본을 절대 덮어쓰지 않는다.** 교정 결과는 항상 새 파일로 나간다.

## 5. 핵심 모델·도구와 선택 이유

전부 **로컬에서만 돈다** — 미공개 방송 전 영상·대본이 클라우드로 나가면 계약
위반이다. 이 제약이 모델 선택 전체를 관통한다(클라우드 API를 쓰면 더 쉬운
자리에서도 로컬 모델을 고른 이유).

| 용도 | 선택 | 이유 |
|---|---|---|
| 전사(STT) | ffmpeg 내장 whisper 필터(whisper.cpp), `ggml-large-v3-turbo` | 별도 설치 없이 이미 쓰는 ffmpeg으로 됨. large 모델이 GPU에서 base보다 오히려 빠르고(23배속 vs 8배속) 훨씬 정확해 품질 낮출 이유가 없었다 |
| 말소리 구간(VAD) | Silero VAD(ONNX, 2MB) | ffmpeg의 음량 기반 검출은 배경음악·잡음에서 무너진다(한 자료에서 30분을 구간 3개로 잘못 잡음). 모델 기반이 최악을 없앤다 |
| 번역(1차) | Ollama 로컬 LLM — 기본 `exaone3.5:7.8b`(한국어 품질 우수, 상업 라이선스 제약 있음), 대안 `qwen2.5:7b-instruct`(Apache-2.0) | 로컬 제약 + 라이선스 선택권을 같이 준다. 3060 Ti 8GB에서 4bit 양자화로 돈다 |
| 화자 분리 | `pyannote/speaker-diarization-community-1`(2026-08-27 도입) | whisper가 화자 구분을 안 준다 — 예능처럼 화자가 빠르게 바뀌는 자리를 `regroup.py`가 한 자막으로 뭉치는 버그의 근본 원인이었다. 4개 후보 중 3.1보다 화자 수 세기·전사 타이밍 정합이 낫다고 공식 문서가 밝힌 최신판을 선택 |
| `--against` 텍스트 유사도 | Ollama 임베딩, `paraphrase-multilingual`(2026-08-27 도입) | 글자 겹침(`SequenceMatcher`)은 의역을 못 잡는다("Mister Cho isn't that you?" vs "Aren't you Mr. Cho?" = 글자 유사도 0.18). 참/거짓 짝 10개로 4개 모델(bge-m3·paraphrase-multilingual·nomic-embed-text-v2-moe·qwen3-embedding:0.6b)을 실측 비교해 분리폭이 가장 큰 것을 골랐다(`checker/embed.py` 주석에 표 있음) |
| BLEU·ROUGE·perplexity | **안 씀** | 시도했다가 걷어냈다. ROUGE-L이 기존 글자 유사도와 값이 같았고, 한국어 특유의 짧은 어절 때문에 BLEU가 자주 0으로 무너짐. `번역-품질-지표` 스킬에 판단 근거 기록 |
| Whisper 파인튜닝 | **안 함(의도적)** | 자막은 대사의 축약본이지 전사가 아니다. 이것으로 ASR을 학습시키면 전사 자체가 축약을 배워버린다 — 전사는 모델 교체로만 개선한다 |
| 번역 LoRA(PEFT) | **아직 안 함** | 최소선 5,000쌍(≈5편)에 아직 못 미침(2026-08-27 기준 1편, 1,453쌍). 문턱값 도달 시 자동 시작하지 않고 사용자에게 먼저 건의하기로 함. `corpus/pairs/`에 (초안, 정답) 짝을 미리 쌓는 중 |

### 개발 환경 특이사항 — 반드시 알아야 함

- **pyannote.audio는 시스템 파이썬에 직접 설치하면 안 된다.** torch>=2.8.0을
  요구하는데, 시스템 파이썬의 torch(2.6.0+cu124)는 torchvision 등 다른
  프로젝트가 물려 쓴다. 실제로 한 번 설치했다가 시스템 torch를 CPU 전용
  2.13.0으로 바꿔버려 되돌린 적이 있다(2026-08-27). **`.venv-diarize/`에
  격리 설치한다.**
- Windows에서 개발, 사용자는 Windows에서 실행. WSL은 Ollama 원격 호출에만
  쓴다(GPU가 Windows 쪽에 있어서).
- ffmpeg 필터 옵션에 절대 경로를 못 쓴다(`C:`의 콜론이 옵션 구분자로 읽힘) —
  작업 폴더 기준 상대 경로만 쓴다.
- ffmpeg 출력은 반드시 `encoding="utf-8"`로 디코드한다. Windows 파이썬 기본은
  cp949라 non-ASCII가 섞이면 스트림이 깨진다.
- 배치 파일 본문은 ASCII만 — cmd가 콘솔 코드페이지로 바이트 단위 파싱을 한다.

### 화자 분리(`--diarize`) 의존성 상태

`.venv-diarize/`에 pyannote.audio + torch 2.13.0+cu126을 격리 설치해
뒀다(시스템 파이썬과 왜 분리했는지는 위 항목 참고). 모델은
`pyannote/speaker-diarization-community-1`(게이팅됨, HF 계정으로 이용조건
동의 + read 권한 토큰 필요 — `checker/diarize.py` 참고, 토큰은
`HF_TOKEN` 환경변수). Windows 사용자 환경변수는 이미 떠 있는 프로세스에
소급 적용 안 된다 — 등록 후 새 셸이 필요하다.

**2026-08-28부터 이 컴퓨터에서 `--diarize`가 막혀 있다 — 코드 문제가
아니다.** `DLL load failed ... 애플리케이션 제어 정책` 오류가 난다.
원인은 Windows 11 **Smart App Control**이 켜져 있어서다(`Get-CimInstance
-Namespace root\Microsoft\Windows\Defender -ClassName
MSFT_MpComputerStatus`의 `SmartAppControlState`가 `On`) — 서명 안 되거나
평판 정보 없는 실행 파일·DLL을 자동 차단하는 기능인데, `.venv-diarize`의
torch DLL이 걸린다. 어젯밤(2026-08-27)엔 됐다가 다음날 안 됐다 — 평판
재평가가 나중에 이뤄졌을 가능성이 크다.

**끄면 해결되지만 사용자가 껐다 켤 수 없는 기능이다**(마이크로소프트가
의도적으로 단방향으로 설계 — 다시 켜려면 윈도우 초기화가 필요하다).
그래서 **사용자 결정(2026-08-28): 끄지 않는다. `--diarize` 없이
진행한다.** 이 컴퓨터에서 화자 분리가 다시 필요해지면 이 상태부터
확인한다 — DLL 경로나 코드 문제로 오판해서 시간 낭비하지 않는다. 다른
컴퓨터(예: 노트북)로 옮기면 될 수도 있다(그쪽 Smart App Control 상태에
달렸다).

## 6. 그동안 찾아 고친 구조적 버그 (재발 방지용 요약)

전부 `checker/`에 남아 자동으로 다음 영상부터 적용된다. 상세 재현 과정은
`docs/BACKLOG.md`에 있다 — 여기는 "무엇을, 왜"만.

- **whisper 무음 환각**: 완전한 침묵에서도 whisper가 자신 있게 글자를
  지어낸다. 말소리 구간(VAD)과 전혀 안 겹치는 전사 조각을 걸러낸다. 이
  필터를 만들다가 **VAD 자체가 도중에 멎는** 경우(컨테이너 손상 등)를
  놓쳐 실제 대사 6분을 통째로 지운 회귀를 자체 발견·수정했다 — "검출기가
  못 찾았다"와 "검출기가 멎었다"는 다른 사건이다.
- **다중 화자 병합 폭주**: `regroup.py`가 whisper 조각을 합칠 때 화자
  교체를 못 봐서, 빠른 대화 주고받기를 한 자막에 뭉쳤다. 스포팅 아웃점이
  거기서 수백~수천ms 밀렸다. 1차로 `max_shift_ms` 상한(2026-08-27)으로
  막았고, 근본 원인은 화자 분리 도입(5번 표)으로 해결 중.
- **재분할이 문장 경계를 안 봄**: 글자 수가 남으면 서로 다른 발화 여러 개를
  한 자막에 묶어 냈다. `force_sentence_split`으로 문장이 끝나는 자리는
  글자 수와 무관하게 가른다.
- **번역 출력에 형식 오염**: 모델이 번역문 전체를 마크다운(`**...**`)으로
  감싸거나, `원래 번역 → 고친 번역` 형식의 자기수정을 그대로 남기거나,
  `**참고:**` 같은 설명을 덧붙였다. 셋 다 프롬프트에 이미 있던 형식(용어집
  힌트가 `A → B`를 씀)을 모델이 따라 하다 생긴 오염으로 보인다. 전부 후처리
  단계에서 벗겨낸다(`checker/translate.py`).
- **검사기가 미구현 항목을 조용히 통과시킴**: `--check` 모드는 미구현 검사
  목록을 보여줬는데 `--generate` 모드는 그 줄 자체가 없었다 — 검사 안 한
  것이 "위반 없음"처럼 보였다. 두 경로가 같은 정보를 내도록 맞췄다.
- **`--against`의 가짜 짝짓기**: 시간이 가장 가까운 것끼리 기계적으로
  짝짓다 보니, 자막 개수가 다르면(캡션을 우리가 못 만드는 등) 전혀 다른
  대사끼리 짝지어져 통계가 왜곡됐다. 캡션 제외 + 유사도 하한 + 길이 하한으로
  거르는 절차를 세웠다(`정답지-대조-진단` 스킬).
- **`--generate --passes`가 조용히 1차만 하고 2차·3차를 건너뜀
  (2026-08-27 밤)**: `stage_revise` 호출이 cli.py의 다른 분기("받은 TC에
  번역만 얹는" 경로, `--generate` 없이 `--translate`만 켠 경우)에만 있었다.
  `--generate --translate --passes 3`를 켜면 그 조건이 거짓이 되어 2차·3차
  전체가 에러 없이 스킵됐다 — 로그에 "2차"·"3차" 진행 표시가 아예 없는데도
  아무 경고가 안 났다. `generate()` 함수 자체에 `passes`를 붙여 어느 CLI
  분기를 타든 같은 경로를 쓰게 고쳤다.
- **2차·3차 결과에 `[pass 2]`·`**Notes:**` 같은 모델 메타 설명이 그대로
  남음(2026-08-27 밤, 위 버그를 고친 뒤 실전 검증 중 발견)**: 원인 둘.
  (1) `revise.py`의 표지 제거 정규식이 문자열 **맨 앞**만 봤는데,
  `_parse_numbered`가 번호 없는 줄을 앞 번호에 이어 붙이므로 표지가 합쳐진
  문자열의 **중간 줄**에서 시작할 수 있었다 — 줄마다 보게 고쳤다.
  (2) `revise.py`에는 1차용 흘림 걸러내기(`_strip_trailing_notes`,
  `_strip_markdown_wrap`)가 아예 없었다 — 표지 제거 정규식 하나뿐이었다.
  2차·3차도 같은 모델이 내는 같은 흘림을 그대로 겪는다는 걸 놓쳤다. 재검증
  (v12)에서 흘림 0건 확인.
- **`revision_report`가 여러 회차를 첫 회차 이름 하나로 합산**: "2차에서
  1207개를 고쳤습니다"처럼 나왔는데, 2차 대상 자막이 1114개뿐이라 애초에
  2차 혼자 낼 수 없는 숫자였다 — 2차+3차 합산값을 `revisions[0].stage`
  이름으로만 세고 있었다. 회차별로 나눠서 센다.

## 7. 미해결 — 다음 사람이 볼 것

우선순위 순서는 아니다. 각 항목이 왜 아직 안 끝났는지가 더 중요하다.

- **영어(그 외 언어) 2차·3차 검수가 없다.** `checker/revise.py`는 한국어
  전용이다. 1차(오역만 없이 직역) 다음 단계(맥락·관용구·말맛·압축)가
  영어·중국어·일본어엔 아예 없어서, 번역 완성도가 1차 수준에 머문다. 만들려면
  각 언어의 실제 자막 압축·문체 관행을 조사해야 한다(추측 금지 — 규칙 9).
- **화면 캡션(강제 자막, forced narrative)을 못 만든다.** OCR이 없다. 정답
  자막의 약 10%가 이 종류다 — 이게 있는 한 어떤 영상도 정답과 100% 못
  맞춘다. 이론적 상한이 있다는 뜻이지 버그는 아니다.
  `detect_bottom_text()`(media.py)가 화면 아래 글자 유무를 짐작은 하지만
  글자를 읽지는 못한다.
- **영상 파일 자체 손상은 복구 불가.** 예능A 15·16회처럼 컨테이너가
  손상된 자료는 whisper가 그 지점에서 짧게 결손을 낸다(46~103개 지점,
  9~10% 대사 손실). 코드로 못 고친다 — 근거만 `rules/learned/`에 남기고
  받아들인다.
- **whisper 반복 환각(hallucination loop)에 대한 코드 차원 대응이 없다.**
  같은 짧은 구절이 비정상적으로 여러 번 반복 전사되는 사례를 확인했다
  (2026-08-27, 예능A 15회 "미스터 조?"/"올라!" 두 자리). 처음엔 이걸
  다중 화자 병합 버그로 오판했다 — `--diarize`를 붙여 실전 검증해 보니
  이 자리는 pyannote가 애초에 **한 명이 계속 말하는 구간**으로 본다(전화
  통화 장면, 화자 교체가 아니라 같은 사람이 같은 말을 반복). 즉 원인은
  화자 분리 부재가 아니라 whisper 자체의 반복 환각이었다 — 화자 분리를
  붙여도 이 예시는 그대로 남는다. 아직 다른 작품에서 재현을 못 봐서
  (`CLAUDE.md` 규칙 12 — 최소 2편 근거) 코드 버그로 승격은 안 했다.
- **LoRA(PEFT) 미시작.** 위 5번 표 참고. `corpus/pairs/`에 쌓는 중이고
  아직 학습 스크립트·평가 방법 자체가 없다 — 이건 데이터가 아니라 인프라가
  없는 상태다.
- **`--diarize`는 실전 검증 끝났고 정상 작동한다(2026-08-27).** 다만 검증
  과정에서 진짜 버그 하나를 더 찾아 고쳤다 — `merge_cues()`가 화자를
  비교할 때 `previous.end_ms`와 `event.start_ms`를 봤는데, 간격이 0인
  병합(whisper 조각이 딱 붙은 가장 흔한 경우)에서는 이 둘이 같은 시각이라
  비교가 항상 무의미했다. 각 조각 자체의 중간 지점을 비교하도록 고친 뒤
  실제로 병합 개수가 바뀌는 것을 확인했다(예능A 15회: 1103→1114).
  **교훈**: 유닛 시험은 통과했지만(간격 50ms로 짜서 이 사례를 못 잡았다)
  실전 데이터로 돌려 보고서야 드러났다 — 화자 정보처럼 실제 값의 분포가
  중요한 로직은 합성 시험만으로 부족할 수 있다.
- **화자 이름을 못 채운다(의도적 설계, 버그 아님).** 화자 분리는 "1번·2번
  화자가 다른 사람"까지만 안다. 실제 이름은 대본이 있어야 하고, 없으면
  사람이 영상을 보고 채운다 — 이름을 추측해서 채우지 않는다(규칙 3).
