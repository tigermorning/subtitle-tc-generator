# 엔지니어링 핸드오프 — 팀 합류자를 위한 문서

이 문서는 `docs/BACKLOG.md`(날짜순 작업 기록)를 대신하지 않는다. 여기는 **"왜
이렇게 만들었는가"와 "지금 무엇이 비어 있는가"만** 담는다. 과정을 시간순으로
쫓고 싶으면 `BACKLOG.md`를, 작업 규칙 자체를 보려면 `CLAUDE.md`를 본다.

**살아있는 문서다.** 결정이 바뀌거나 새 모델을 들이거나 오래된 미해결 항목이
풀리면 이 파일을 그때그때 고친다. 날짜 붙은 회의록이 아니라 **지금 상태의
지도**로 유지한다 — 오래된 항목은 지우거나 고치지, "2026-08-27에는 이랬음"
식으로 쌓아두지 않는다(그건 BACKLOG.md의 역할이다).

## 1. 무엇을 만드는가

방송·OTT용 자막(TC + SDH + 번역)을 사람 작업자 수준으로 초벌 생성하는 도구다.
납품 대상은 발주처(넷플릭스 등)마다 다른 정식 스타일 가이드를 따라야 하고,
결과물은 항상 **사람이 검수·수정하는 초안**이다 — 완전 자동화가 목표가
아니다(아래 4번 "설계 철학" 참고).

두 축이 있다.
- **TC(타임코드) 작업자**: 말소리를 화면 단위로 끊고 인점·아웃점을 맞춘다.
- **자막(SDH·번역) 작업자**: 그 화면 안에 들어갈 텍스트를 쓴다(원어 그대로
  받아쓰거나, 다른 언어로 옮긴다).

이 도구는 두 역할을 **하나의 파이프라인**으로 자동화하고, 발주처 규정 검사기
(`checker/`)로 사람이 볼 것만 추려낸다.

## 2. 파이프라인 — 순서가 설계의 전부다

```
①전사 -> ②대조(대본 있으면) -> ③번역 -> ④재분할 -> ⑤글자수·스포팅 규정
transcribe.py  align.py          translate.py  resplit.py  timing.py / checks.py
```

이 순서를 바꾸면 결과가 구조적으로 나빠진다(`CLAUDE.md` 규칙 1).

- **전사가 글자 수를 무시하는 이유**: whisper의 `max_len`으로 자르면 문장이
  중간에 끊긴 채 굳는다. 사람도 먼저 다 받아쓰고 나중에 나눈다.
- **재분할이 번역 뒤에 오는 이유**: 원어 기준으로 미리 끊으면 번역문(특히
  한국어)이 그 경계에 갇힌다. 언어마다 문장 구조가 달라 끊는 자리도 달라야
  한다.
- **글자 수가 맨 끝인 이유**: 발주처 규정(줄당 글자 수·읽기 속도)은 **번역문
  기준**이다. 원어 스크립트에 규정을 대는 것은 시간 낭비다.

## 3. 규정(rule) 3계층

```
rules/<플랫폼>/        공식 문건에서 옮긴 값. source.official: true
rules/learned/<플랫폼>/ 정답 자막에서 관측한 값. source.origin: learned
코드 기본값             위 둘 다 없을 때만
```

**학습값이 규정을 덮어쓰지 않는다.** 배운 값이 `rules/<플랫폼>/`를 고치는
일은 없다 — 관측이 공식 문건과 다르면 그건 승격이 아니라 "지적"으로 남긴다.
규정으로 승격하는 유일한 길은 사람이 확인하는 것이다(`CLAUDE.md` 규칙 11).

**`rules/genre/`가 플랫폼 규정 위에 얹힌다.** 예능·다큐처럼 장르가 요구하는
값(예: 병합 상한 2초)은 플랫폼과 별개 계층이다.

**`--lock-timecodes`**: 이미 TC 작업이 끝난 파일에 번역만 붙이는 실무 사례를
위한 모드. 재분할·스포팅을 전부 막고, `--fix-timing`과 같이 쓰면 오류를 낸다
(조용히 무시하지 않는다 — `CLAUDE.md` 규칙 8).

**정답지 학습은 두 층(A/B)이고, `genre_maturity`가 그 경계를 관리한다**
(`CLAUDE.md` 규칙 13, 2026-08-30):

```
A. 정답지-학습    정답 자막만 재서 통계·관행을 뽑는다. 영상·GPU 불필요,
                 비용 거의 0. 정답지 있는 영상은 예외 없이 이것부터 한다.
B. 정답지-대조-진단  --generate로 blind 초안을 만들고 --against로 대조해
                 checker/ 코드 자체의 구조 버그를 찾는다. whisper 전사가
                 필요해 비용이 크다.
```

A만으로 충분한지(=B를 계속 돌려야 하는지)는 `docs/corpus_status.yaml`의
`genre_maturity`에 발주처+장르별로 기록한다 — 연속 3편(`threshold`)을 B로
대조했는데 새 구조 버그가 0건(`clean_streak`)이면 "성숙" 후보이지만,
**사람이 확인해야만** `matured: true`가 된다(자동 전환 없음, 규칙 11 승격
경로와 같은 이유). 성숙 판정 후에도 새 이상이 보이면 `clean_streak`은 0으로
리셋된다. 절차는 `.claude/skills/정답지-학습/`·`.claude/skills/정답지-대조-진단/`에
코드화돼 있다.

## 4. 설계 철학 — 세 가지가 반복해서 나온다

1. **어느 쪽도 정답으로 두지 않는다.** 전사와 스크립트가 다르면 기계가
   판정하지 않고 표시만 한다. 표기 통일표를 어겨도 고치지 않고 표시한다 —
   문맥상 예외가 실제로 있다.
2. **확실한 근거와 추정을 구분한다.** 파일 안에서 검증 가능한 것(글자 수,
   중복 등)은 자동 교정한다. 영상에서 추정한 것(말소리 구간, 화자 분리,
   화면 캡션 위치)은 **제안만 하고 자동으로 고치지 않는다** — 틀렸을 때
   원인을 사람이 못 찾기 때문이다.
3. **원본을 절대 덮어쓰지 않는다.** 교정 결과는 항상 새 파일로 나간다.

## 5. 핵심 모델·도구와 선택 이유

전부 **로컬에서만 돈다** — 미공개 방송 전 영상·대본이 클라우드로 나가면 계약
위반이다. 이 제약이 모델 선택 전체를 관통한다(클라우드 API를 쓰면 더 쉬운
자리에서도 로컬 모델을 고른 이유).

| 용도 | 선택 | 이유 |
|---|---|---|
| 전사(STT) | ffmpeg 내장 whisper 필터(whisper.cpp), `ggml-large-v3-turbo` | 별도 설치 없이 이미 쓰는 ffmpeg으로 됨. large 모델이 GPU에서 base보다 오히려 빠르고(23배속 vs 8배속) 훨씬 정확해 품질 낮출 이유가 없었다 |
| 말소리 구간(VAD) | Silero VAD(ONNX, 2MB) | ffmpeg의 음량 기반 검출은 배경음악·잡음에서 무너진다(한 자료에서 30분을 구간 3개로 잘못 잡음). 모델 기반이 최악을 없앤다 |
| 번역(1차) | Ollama 로컬 LLM — 기본 `exaone3.5:7.8b`(한국어 품질 우수, 상업 라이선스 제약 있음), 대안 `qwen2.5:7b-instruct`(Apache-2.0) | 로컬 제약 + 라이선스 선택권을 같이 준다. 3060 Ti 8GB에서 4bit 양자화로 돈다 |
| 화자 분리 | `pyannote/speaker-diarization-community-1`(2026-08-27 도입) | whisper가 화자 구분을 안 준다 — 예능처럼 화자가 빠르게 바뀌는 자리를 `regroup.py`가 한 자막으로 뭉치는 버그의 근본 원인이었다. 4개 후보 중 3.1보다 화자 수 세기·전사 타이밍 정합이 낫다고 공식 문서가 밝힌 최신판을 선택 |
| `--against` 텍스트 유사도 | Ollama 임베딩, `paraphrase-multilingual`(2026-08-27 도입) | 글자 겹침(`SequenceMatcher`)은 의역을 못 잡는다("Mister Cho isn't that you?" vs "Aren't you Mr. Cho?" = 글자 유사도 0.18). 참/거짓 짝 10개로 4개 모델(bge-m3·paraphrase-multilingual·nomic-embed-text-v2-moe·qwen3-embedding:0.6b)을 실측 비교해 분리폭이 가장 큰 것을 골랐다(`checker/embed.py` 주석에 표 있음) |
| BLEU·ROUGE·perplexity | **안 씀** | 시도했다가 걷어냈다. ROUGE-L이 기존 글자 유사도와 값이 같았고, 한국어 특유의 짧은 어절 때문에 BLEU가 자주 0으로 무너짐. `번역-품질-지표` 스킬에 판단 근거 기록 |
| Whisper 파인튜닝 | **안 함(의도적)** | 자막은 대사의 축약본이지 전사가 아니다. 이것으로 ASR을 학습시키면 전사 자체가 축약을 배워버린다 — 전사는 모델 교체로만 개선한다 |
| 번역 LoRA(PEFT) | **아직 안 함** | 최소선 5,000쌍(≈5편)에 아직 못 미침(2026-08-27 기준 1편, 1,453쌍). 문턱값 도달 시 자동 시작하지 않고 사용자에게 먼저 건의하기로 함. `corpus/pairs/`에 (초안, 정답) 짝을 미리 쌓는 중 |

### 개발 환경 특이사항 — 반드시 알아야 함

- **pyannote.audio는 시스템 파이썬에 직접 설치하면 안 된다.** torch>=2.8.0을
  요구하는데, 시스템 파이썬의 torch(2.6.0+cu124)는 torchvision 등 다른
  프로젝트가 물려 쓴다. 실제로 한 번 설치했다가 시스템 torch를 CPU 전용
  2.13.0으로 바꿔버려 되돌린 적이 있다(2026-08-27). **`.venv-diarize/`에
  격리 설치한다.**
- Windows에서 개발, 사용자는 Windows에서 실행. WSL은 Ollama 원격 호출에만
  쓴다(GPU가 Windows 쪽에 있어서).
- ffmpeg 필터 옵션에 절대 경로를 못 쓴다(`C:`의 콜론이 옵션 구분자로 읽힘) —
  작업 폴더 기준 상대 경로만 쓴다.
- ffmpeg 출력은 반드시 `encoding="utf-8"`로 디코드한다. Windows 파이썬 기본은
  cp949라 non-ASCII가 섞이면 스트림이 깨진다.
- 배치 파일 본문은 ASCII만 — cmd가 콘솔 코드페이지로 바이트 단위 파싱을 한다.

### 화면 캡션 인식(`--ocr-scan`) 의존성 상태 (2026-08-30 신설, 같은 날 스모크 테스트+고침 끝)

`.venv-diarize`와 같은 이유로 `.venv-ocr/`에 EasyOCR을 격리 설치했다 —
`requirements-ocr.txt` 참고. 설치·실측·수정·재검증까지 한 세션에서 끝냈다
(2026-08-30, 예능A 19회 "Screwballs S02E19"로).

**1차 실측에서 구조적 문제 둘을 찾았고, 같은 날 바로 고쳤다:**

1. **기본 모드(`detect_bottom_text` 선필터)가 이 영상에서 캡션을 0개 찾았다.**
   원인을 프레임을 직접 열어 확인함(300초·900초·1500초 지점) — 이 예능의
   화면 캡션은 화면 **아래 25%가 아니라 인물 옆(중앙~오른쪽, 세로 중간)**에
   뜬다. `detect_bottom_text`는 이름 그대로 아래쪽만 본다 — 애초에 이 종류
   캡션 위치를 못 잡는 설계다. **고침**: `checker/ocr.py`의 `full_scan` 기본값을
   `True`로 뒤집었다(규칙12: 정확히 다 훑는 것이 빠른 것보다 우선). 옛 방식
   (선필터로 빠르게)은 `--ocr-fast`로 opt-in만 가능하다.
2. **`merge_frames`의 정확 일치 비교가 같은 캡션을 여러 조각으로 쪼갰다.**
   실측: 같은 캡션("우리 마님이 이런데 뭐..?")이 연속된 프레임에서 EasyOCR이
   매번 조금씩 다르게 읽었다("마남이"/"마넘이"/"마남이" — 압축·모션 블러로
   프레임마다 인식이 흔들린다). 완전 일치 비교라 한 캡션이 세 조각으로
   갈렸다. **고침**: `difflib.SequenceMatcher`(표준 라이브러리) 편집 유사도
   비교로 바꿨다(`--ocr-min-similarity`, 기본 0.6). 대표 텍스트는 합쳐진
   프레임 중 신뢰도가 가장 높았던 것을 쓴다.

**재검증**: 같은 40초 클립을 다시 돌려 캡션이 3조각 -> 1개로 병합됨을
확인(0~2000ms, "우리 마남이 / 이런데 뭐 ?", 신뢰도 0.56). `tests/run_tests.py`
에 편집 유사도 케이스 추가, 812건 전부 통과. 읽기 자체는 원래도 잘 됐다
(신뢰도 0.4~0.78, "마님"이 "마남"으로 한 글자만 틀림) — 문제는 위치 가정과
병합 로직이었지 EasyOCR 자체가 아니었다.

**전체 회차(37분)로 회귀 확인 — 세 번째 문제를 가정했다가 검증해서 절반만
맞았다(2026-08-31):** 전체를 돌려보니 캡션 하나가 167초까지 늘어난 사례가
나와, "전이적 드리프트"(직전 캡션의 대표 텍스트와 비교하면 A~B~C~D로 비교
기준이 계속 옮겨가며 서로 다른 캡션이 섞여 이어 붙는 것)로 가정했다.

- **비교 기준을 anchor(그 캡션의 첫 프레임)로 바꾼 것은 맞는 고침이었다** —
  합성 테스트로 실제 드리프트 시나리오를 재현해 확인함(`tests/run_tests.py`).
- **처음에 같이 넣은 `max_duration_ms`(8000ms) 상한은 검증 없이 넣었다가
  되돌렸다.** 167초 구간을 다시 잘라 돌려 보니 여전히 하나로 합쳐졌고(anchor
  비교만으로 이미 정상), 315초·340초 프레임을 직접 열어 확인하니 "Sebastiam/
  Tomy/Scarlet" **이름 캡션이 25초 넘게 픽셀 단위로 그대로**였다 — 167초짜리는
  버그가 아니라 **사실**이었다(정지 화면 코멘터리·이름표 캡션은 실제로 이만큼
  오래 떠 있는다). 상한 기본값을 없앴다(`None`, `--ocr-max-duration`으로 사람이
  켜야만 적용). 증거 없이 상한을 두면 실제로 오래 떠 있는 정상 캡션을 인위적으로
  쪼갠다 — 이 결정 자체가 규칙14(맥락 부패 확인 — 이전 생성물의 추정을 검증
  없이 다음 고침에 그대로 반영하지 않는다)의 사례다.
- **두 번째 독립 근거(311~370초 구간, 상한 되돌리기 전 코드로 돌았지만
  텍스트 자체를 보면 충분함)**: "아무리 그래도 그게 뛰냐"가 62.5초 내내
  검출된 8조각 전부에서 **글자 하나 안 바뀌고** 그대로였다. 이름 캡션
  사례와 별개로, 정적 텍스트가 오래 떠 있는 것이 이 영상에서 드문 일이
  아님을 다시 확인했다.

`tests/run_tests.py` 817건 전부 통과. `checker/ocr.py`의 `merge_frames`
독스트링에 이 판단 과정을 그대로 남겨 뒀다 — 다음에 "지속시간이 이상하다"는
지적이 다시 나오면 여기부터 읽는다.

Smart App Control이 켜져 있으면 `.venv-diarize`의 torch DLL이 막힌 적이
있다(아래 항목) — `.venv-ocr`는 이번엔 문제없이 돌았다.

**2단계(`--generate --ocr`, 2026-08-31)**: 위 1단계(`--ocr-scan`, 보고용)
위에 실제 자막 병합을 얹었다. 자세한 내용은 `docs/BACKLOG.md` T12 참고 —
요약하면 `position.is_forced_narrative()`가 이미 텍스트 마커만으로 화면자막을
판정하고 있어서, 필요했던 건 마커를 입히는 함수 하나뿐이었다.

**3단계(`--ocr-hardsub`, 2026-08-31, 같은 날)**: T12까지는 whisper 대사 위에
얹는 *부가* 캡션이었다 — `[습작] SDH+번역/하드섭(자막필요)/`처럼 자막이 화면
전체에 타 있고 임베디드 트랙이 아예 없는 영상엔 안 맞았다. `tools/corpus_build.py:
90-91`이 "OCR을 거친 것은 정답 자료로 쓰지 않는다"고 이미 못박아 둬서,
`--ocr-hardsub`는 **초안(.ocr-draft.srt)만** 낸다 — 사람이 영상과 대조해
고친 뒤에야 `학습한 TC 및 자막 모음/`에 들어간다(`docs/BACKLOG.md` T13,
`.claude/skills/정답지-학습/SKILL.md`). 실측 중 구조 버그를 하나 더 찾음:
전체 프레임을 읽으면 좌상단 작품명 워터마크·배경 간판 글자가 대사와 섞여
정작 실제 대사가 결과에서 사라졌다 — `_extract_frames()`에 화면 아래
`band`(기본 0.25) 자르기를 추가해 고침(`--ocr-scan`/`--ocr`은 캡션 위치가
안 정해져 있어 여전히 `band=None`).

### 화자 분리(`--diarize`) 의존성 상태

`.venv-diarize/`에 pyannote.audio + torch 2.13.0+cu126을 격리 설치해
뒀다(시스템 파이썬과 왜 분리했는지는 위 항목 참고). 모델은
`pyannote/speaker-diarization-community-1`(게이팅됨, HF 계정으로 이용조건
동의 + read 권한 토큰 필요 — `checker/diarize.py` 참고, 토큰은
`HF_TOKEN` 환경변수). Windows 사용자 환경변수는 이미 떠 있는 프로세스에
소급 적용 안 된다 — 등록 후 새 셸이 필요하다.

**2026-08-28부터 이 컴퓨터에서 `--diarize`가 막혀 있다 — 코드 문제가
아니다.** `DLL load failed ... 애플리케이션 제어 정책` 오류가 난다.
원인은 Windows 11 **Smart App Control**이 켜져 있어서다(`Get-CimInstance
-Namespace root\Microsoft\Windows\Defender -ClassName
MSFT_MpComputerStatus`의 `SmartAppControlState`가 `On`) — 서명 안 되거나
평판 정보 없는 실행 파일·DLL을 자동 차단하는 기능인데, `.venv-diarize`의

재평가가 나중에 이뤄졌을 가능성이 크다.

**끄면 해결되지만 사용자가 껐다 켤 수 없는 기능이다**(마이크로소프트가
의도적으로 단방향으로 설계 — 다시 켜려면 윈도우 초기화가 필요하다).
그래서 **사용자 결정(2026-08-28): 끄지 않는다. `--diarize` 없이
진행한다.** 이 컴퓨터에서 화자 분리가 다시 필요해지면 이 상태부터
확인한다 — DLL 경로나 코드 문제로 오판해서 시간 낭비하지 않는다. 다른
컴퓨터(예: 노트북)로 옮기면 될 수도 있다(그쪽 Smart App Control 상태에
달렸다).

## 6. 그동안 찾아 고친 구조적 버그 (재발 방지용 요약)

전부 `checker/`에 남아 자동으로 다음 영상부터 적용된다. 상세 재현 과정은
`docs/BACKLOG.md`에 있다 — 여기는 "무엇을, 왜"만.

- **whisper 무음 환각**: 완전한 침묵에서도 whisper가 자신 있게 글자를
  지어낸다. 말소리 구간(VAD)과 전혀 안 겹치는 전사 조각을 걸러낸다. 이
  필터를 만들다가 **VAD 자체가 도중에 멎는** 경우(컨테이너 손상 등)를
  놓쳐 실제 대사 6분을 통째로 지운 회귀를 자체 발견·수정했다 — "검출기가
  못 찾았다"와 "검출기가 멎었다"는 다른 사건이다.
- **다중 화자 병합 폭주**: `regroup.py`가 whisper 조각을 합칠 때 화자
  교체를 못 봐서, 빠른 대화 주고받기를 한 자막에 뭉쳤다. 스포팅 아웃점이
  거기서 수백~수천ms 밀렸다. 1차로 `max_shift_ms` 상한(2026-08-27)으로
  막았고, 근본 원인은 화자 분리 도입(5번 표)으로 해결 중.
- **재분할이 문장 경계를 안 봄**: 글자 수가 남으면 서로 다른 발화 여러 개를
  한 자막에 묶어 냈다. `force_sentence_split`으로 문장이 끝나는 자리는
  글자 수와 무관하게 가른다.
- **번역 출력에 형식 오염**: 모델이 번역문 전체를 마크다운(`**...**`)으로
  감싸거나, `원래 번역 → 고친 번역` 형식의 자기수정을 그대로 남기거나,
  `**참고:**` 같은 설명을 덧붙였다. 셋 다 프롬프트에 이미 있던 형식(용어집
  힌트가 `A → B`를 씀)을 모델이 따라 하다 생긴 오염으로 보인다. 전부 후처리
  단계에서 벗겨낸다(`checker/translate.py`).
- **검사기가 미구현 항목을 조용히 통과시킴**: `--check` 모드는 미구현 검사
  목록을 보여줬는데 `--generate` 모드는 그 줄 자체가 없었다 — 검사 안 한
  것이 "위반 없음"처럼 보였다. 두 경로가 같은 정보를 내도록 맞췄다.
- **`--against`의 가짜 짝짓기**: 시간이 가장 가까운 것끼리 기계적으로
  짝짓다 보니, 자막 개수가 다르면(캡션을 우리가 못 만드는 등) 전혀 다른
  대사끼리 짝지어져 통계가 왜곡됐다. 캡션 제외 + 유사도 하한 + 길이 하한으로
  거르는 절차를 세웠다(`정답지-대조-진단` 스킬).
- **`--generate --passes`가 조용히 1차만 하고 2차·3차를 건너뜀
  (2026-08-27 밤)**: `stage_revise` 호출이 cli.py의 다른 분기("받은 TC에
  번역만 얹는" 경로, `--generate` 없이 `--translate`만 켠 경우)에만 있었다.
  `--generate --translate --passes 3`를 켜면 그 조건이 거짓이 되어 2차·3차
  전체가 에러 없이 스킵됐다 — 로그에 "2차"·"3차" 진행 표시가 아예 없는데도
  아무 경고가 안 났다. `generate()` 함수 자체에 `passes`를 붙여 어느 CLI
  분기를 타든 같은 경로를 쓰게 고쳤다.
- **2차·3차 결과에 `[pass 2]`·`**Notes:**` 같은 모델 메타 설명이 그대로
  남음(2026-08-27 밤, 위 버그를 고친 뒤 실전 검증 중 발견)**: 원인 둘.
  (1) `revise.py`의 표지 제거 정규식이 문자열 **맨 앞**만 봤는데,
  `_parse_numbered`가 번호 없는 줄을 앞 번호에 이어 붙이므로 표지가 합쳐진
  문자열의 **중간 줄**에서 시작할 수 있었다 — 줄마다 보게 고쳤다.
  (2) `revise.py`에는 1차용 흘림 걸러내기(`_strip_trailing_notes`,
  `_strip_markdown_wrap`)가 아예 없었다 — 표지 제거 정규식 하나뿐이었다.
  2차·3차도 같은 모델이 내는 같은 흘림을 그대로 겪는다는 걸 놓쳤다. 재검증
  (v12)에서 흘림 0건 확인.
- **`revision_report`가 여러 회차를 첫 회차 이름 하나로 합산**: "2차에서
  1207개를 고쳤습니다"처럼 나왔는데, 2차 대상 자막이 1114개뿐이라 애초에
  2차 혼자 낼 수 없는 숫자였다 — 2차+3차 합산값을 `revisions[0].stage`
  이름으로만 세고 있었다. 회차별로 나눠서 센다.
- **드라마 병합 상한이 예능 기준(2초)을 상속 안 받고 기본값(4초)에 머묾
  (2026-08-30, 드라마B E01)**: `rules/genre/variety.yaml`은 590행
  근거로 `timecode.merge_max_ms: 2000`을 이미 걸어 뒀는데 `drama.yaml`엔
  이 키가 없었다 — 드라마 권장(2~3초)이 `spotting.recommended_ms`에
  적혀만 있고 병합 단계엔 안 이어졌다. 표시 시간이 정답의 거의 2배(2900~
  4400ms vs 1794~2127ms)로 나온 원인이었다. `merge_max_ms: 3000`(권장
  상한)을 넣었다.
- **whisper 필터가 신뢰도를 안 줘서 환각을 못 걺**: ffmpeg 내장 whisper
  필터는 srt·json 어느 출력에도 `avg_logprob` 같은 신뢰도 값이 없다(직접
  테스트로 확인). 전사 백엔드를 faster-whisper(ctranslate2)로 바꿔 신뢰도를
  받게 했다. 신뢰도만으론 부족했다 — 언어를 강제 지정(`--whisper-lang
  ko`)하면 정확히 옮긴 외국어 대사도 신뢰도가 낮게 나온다. **신뢰도 낮음 +
  글자 밀도(3 CPS) 낮음이 같이 있을 때만** 환각으로 본다(정밀도 위해
  재현율을 일부 포기하는 절충).
- **외국어 대사가 번역 안 되고 그대로 남음**: 정답 SDH는 일본어 대사를
  전부 한국어로 옮기고 `[남자가 일어로]`처럼 언어 표시를 붙이는데, 우리는
  전사만 하고 안 옮겼다(disney/ko-sdh.yaml의 `translate_if_plot_pertinent_
  and_foreign`이 이미 있었는데 화면자막용인 줄 알고 무시했었다 — 실제로는
  대사에도 적용됨을 정답 대조로 확인). `checker/foreign_dialogue.py`를
  새로 만들어 로컬 번역기로 옮기되, 화자 이름은 지어내지 않고(`[일본어]`만
  표시) 옮긴 자리마다 notes에 "확인 필요"를 남긴다. 번역 결과에 한글이
  하나도 없으면(모델이 지시를 무시하고 원문/다른 외국어를 돌려준 경우)
  번역 실패로 보고 원문을 그대로 둔다.
- **문맥 불일치 검사(`--check-context`)가 이미 있었는데 안 쓰고 있었음**:
  whisper가 비슷한 소리를 다른 말로 잘못 듣어도 문법은 멀쩡한 문장을 낸다
  — `context_check.py`가 로컬 LLM으로 앞뒤 문맥과 맞는지 보는 기능인데
  CLI 플래그(`--check-context`)를 아무도 안 켜고 있었다. 켜니 E01에서
  83곳 검출 — 신뢰도·글자밀도 기반 환각 검사(63곳)와 거의 안 겹친다.
  둘은 서로 다른 오류를 잡는다: 통계 검사는 "시간 대비 글자가 적다", 문맥
  검사는 "문법은 되는데 뜻이 안 통한다".
- **whisper 전사가 같은 영상·같은 명령에도 매번 다르게 나옴**: faster-whisper
  전환 후 실측(같은 명령 5번) — 세그먼트 수 290·705·709·747·756개.
  4번은 700대에 몰렸는데 1번(290)만 확 튀었고, 그때가 우리 자체 VAD(결정적)가
  찾은 말소리 구간(660개)보다도 적었다. "세그먼트가 말소리 구간의 90%
  미만이면 실패로 의심"해 한 번 더 전사하고, 매 실행 결과를
  `whisper_retry_log.jsonl`에 남긴다(표본이 적어 임계값은 가설 — 데이터
  쌓이는 대로 재검토 예정).
- **"VAD가 못 잡으면 whisper가 지어낸 것"이라는 전제가 배경음악 있는
  구간에서 깨짐(2026-08-31, 영화B en-sdh 정답 대조)**: VAD 안
  겹치는 조각을 조용히 지우던 필터가 배경음악 깔린 65초·18초 구간에서
  whisper가 정확히 받아 적은 진짜 대사("Hello!"·"Where is the fuel?"·
  "Wait." 등)까지 함께 지웠다. 게다가 그 자리 주석은 "지우지 않고 알린다"고
  적혀 있었는데 실제 코드는 지우고 있었다(규칙 4 위반). `generate.py`의
  `has_vad_support()`로 분리해 **지우지 않고 표시만** 하도록 고쳤다 —
  기존 환각 의심(밀도·신뢰도) 검사와 별개 목록으로 알린다. 같은 whisper
  캐시로 고치기 전/후 재생성해 확인: 짝지음 1198→1503개(54.3%→68.1%),
  세 예시 구간 중 둘은 대사가 살아났고 나머지 하나(220~240초, "Red
  leather, yellow leather.")는 원인이 달랐다 — whisper 자체가 그 대사를
  옆 문장에 통째로 삼켜 애초에 전사를 안 했다(VAD와 무관, 다른 갈래의
  한계). 부작용: "군더더기"(정답에 없는 우리 자막) 166→345개로 늘었다 —
  전엔 지워서 안 보이던 진짜 환각이 이제 표시만 되어 최종 자막에 남기
  때문이다(사람이 편집 중 지워야 한다).
- **whisper의 "유명한" 침묵 환각 문구는 텍스트만으로도 판정 가능해서
  자동으로 지운다(2026-08-31, 위 항목 부작용을 영화A로 검증하다
  발견)**: 위 VAD 고침 뒤 영화A 오프닝에서 "Transcribed by ESO,
  translated by —"·대시(`—`)만 있는 조각이 수십 개 드러났다 —
  whisper.cpp·openai-whisper 커뮤니티에 널리 보고된, 유튜브 자동자막 학습
  흔적으로 보이는 환각이다. VAD 안 겹침과 달리 이건 **오디오 추정이 아니라
  텍스트 자체로 확인되는 사실**이라(규칙 4) `_is_known_hallucination()`으로
  자동으로 지운다(문구 사전 매칭 + 글자다운 글자가 하나도 없는 조각).
  영화A에서 117개 지움. **주의**: 이 고침 뒤 `--against` 짝지음
  숫자가 1187→1117개로 오히려 줄었다 — 퇴보가 아니라 스킬 4번이 경고한
  "가짜 짝짓기"가 걷힌 것이다(직접 확인: 지워진 문구 다수가 근처 진짜
  정답 대사와 시간만 가까워 억지로 짝지어져 있었다. 그래서 유사도 중앙값은
  오히려 올랐다, 0.46→0.50). **짝지음 개수만 보고 판단하지 않는다** —
  군더더기 개수(111→94)·유사도 중앙값을 같이 봐야 한다.
- **whisper가 20~30초씩 통째로 환각 루프에 빠져 그 구간 실제 대사를
  전부 잃는 사례(2026-08-31, 영화B·영화A 정답 대조에서
  총 3번 확인)**: 위 두 항목으로는 못 막았다 — 텍스트가 진짜(영화B
  "Red leather, yellow leather.")거나 유명 문구라 지워지긴 해도(영화A
  "Transcribed by —" 두 곳, 27~30초) 그 밑에 깔린 실제 대사 자체를
  whisper가 애초에 안 만들었기 때문이다. `checker/transcribe.py`의
  `_faster_whisper_transcribe()`에 `condition_on_previous_text=False`
  (직전 텍스트로 다음 조각을 조건화하지 않음 — 한 번 헛것을 뱉으면 다음
  조각도 그 문맥을 물고 환각을 반복하는 전이를 끊는다)와
  `hallucination_silence_threshold=2.0`(`word_timestamps=True`가 있어야
  작동, faster-whisper 자체 기능 — 무음에서 환각이 이어지면 건너뜀) 둘을
  추가했다. 영화A로 검증(같은 영상, 새로 전사): 두 환각 루프 구간
  모두 실제 대사로 복원 확인(정답 15개 중 11개, 13개 중 13개 커버).
  전체 지표도 같이 좋아졌다 — 짝지음 1117→1456(51.4%→67.0%), 유사도
  중앙값 0.50→0.77, 인점 편향 +240ms→+60ms, 아웃점 +771ms→+86ms(앞서
  "짧은 리액션 컷 과다연장"으로 보였던 것도 이 환각 루프가 근본 원인이었다
  — 같이 사라짐). **주의**: faster-whisper 로드가 Smart App Control로
  간헐적으로 막힌 적 있다(`DLL load failed`) — 실패하면 ffmpeg 내장
  whisper로 조용히 대체되는데, 그쪽엔 이 두 옵션이 없다. 로그에
  "(faster-whisper)" 표시가 있는지 확인하고 결과를 판단할 것.
  **영화B로 재검증(2026-08-31, 같은 날)**: 원래 문제였던 세
  구간(125~190초·220~240초·378~396초) 전부 실제 대사로 복원 확인 — 고침
  자체는 두 작품 모두에서 검증됨. 다만 **전체 지표는 오히려 살짝
  내려갔다**(짝지음 68.1%→64.3%, 인점 편향 +90→+135ms) — 새 버그가
  아니라 두 가지가 겹친 결과로 판단: ① whisper 전사는 같은 영상도 실행마다
  달라진다(이미 위에 기록된 특성), ② `condition_on_previous_text=False`가
  문맥 참고를 끊은 대가로 애매한 대사를 더 잘못 듣는 사례를 실측함
  ("This is first contact!"를 "this is cursed contact"로). 8초 넘는 긴
  세그먼트가 35개 생겼는데(그레이스의 긴 혼잣말 — 영화B는 예능처럼
  화자 하나가 오래 말을 잇는 장면이 많다) `resplit_all`이 이미 잘 쪼개고
  있어 이건 구조 문제가 아님(직접 확인, 13개 대 정답 10개로 잘 나뉨).
  **결론**: 대사 통째 손실이라는 원래 문제는 고쳐졌고, 아깝지만 감수하는
  대가(가끔 오청)가 있다 — 유리하게만 보고하지 않는다(규칙11 보고 방식과
  같은 정신). 더 깊이 팔 신호는 안 보인다.

## 7. 미해결 — 다음 사람이 볼 것

우선순위 순서는 아니다. 각 항목이 왜 아직 안 끝났는지가 더 중요하다.

- **영어(그 외 언어) 2차·3차 검수가 없다.** `checker/revise.py`는 한국어
  전용이다. 1차(오역만 없이 직역) 다음 단계(맥락·관용구·말맛·압축)가
  영어·중국어·일본어엔 아예 없어서, 번역 완성도가 1차 수준에 머문다. 만들려면
  각 언어의 실제 자막 압축·문체 관행을 조사해야 한다(추측 금지 — 규칙 9).
- ~~화면 캡션(강제 자막, forced narrative)을 자막으로 못 만든다~~ 〔2026-08-31
  풀림〕. `--generate --ocr --fn-marker <표식>`으로 EasyOCR이 읽은
  화면 캡션을 대사 자막에 실제로 합친다(`checker/ocr.py`의
  `captions_to_events`/`merge_captions`, `docs/BACKLOG.md` T12). 마커를
  입혀 `position.is_forced_narrative()`가 알아보게 하므로 겹침 검사(C10·
  DP22·CP23)와 T10(`quote_role_swapped`)·T11(화면자막·대사 병합 금지)도
  그대로 걸린다(T10/T11도 같은 날 구현). 실측(예능A 19회 일부
  구간)으로 대사+캡션 병합·번호 재부여·신뢰도 낮은 캡션 노트까지 확인함.
  GUI(`app/`)에도 같은 날 붙였다 — 툴바 체크박스, `_job_rules()` 사전
  확인, 표에서 캡션 줄 색·툴팁 구분. 붙이면서 `CheckJob`/`TranslateJob`/
  `ReviseJob`/`PolishJob`이 `Event`를 다시 만들 때 `kind`를 안 넘기던
  버그도 같이 고침(안 고쳤으면 OCR 캡션이 검사·번역 단계를 거치는 순간
  다시 대사로 보였을 것). **GUI 검증은 옆 리포의 venv로 실제로 했다** —
  `korean-subtitle-corrator/.venv/Scripts/python.exe`에 PySide6가 이미
  있다(pre-commit 훅이 app/ 건드릴 때 이 경로를 알려준다). 그걸로
  `SubtitleModel`의 캡션 색·툴팁을 직접 띄워 확인, `tests/run_tests.py`도
  839→871건(PySide6 몫까지)으로 전부 통과. 창 띄워 마우스로 눌러 보는
  것만 사용자 몫. **여전히 안 된 것**:
  `pipeline.py`의 `stage_ocr_captions` 등록(그 선언 자체를 CLI·GUI 다
  안 쓴다는 게 이미 확인됨 — 별도 리팩터).
- **영상 파일 자체 손상은 복구 불가.** 예능A 15·16회처럼 컨테이너가
  손상된 자료는 whisper가 그 지점에서 짧게 결손을 낸다(46~103개 지점,
  9~10% 대사 손실). 코드로 못 고친다 — 근거만 `rules/learned/`에 남기고
  받아들인다.
- **whisper 반복 환각(hallucination loop)에 대한 코드 차원 대응이 없다.**
  같은 짧은 구절이 비정상적으로 여러 번 반복 전사되는 사례를 확인했다
  (2026-08-27, 예능A 15회 "미스터 조?"/"올라!" 두 자리). 처음엔 이걸
  다중 화자 병합 버그로 오판했다 — `--diarize`를 붙여 실전 검증해 보니
  이 자리는 pyannote가 애초에 **한 명이 계속 말하는 구간**으로 본다(전화
  통화 장면, 화자 교체가 아니라 같은 사람이 같은 말을 반복). 즉 원인은
  화자 분리 부재가 아니라 whisper 자체의 반복 환각이었다 — 화자 분리를
  붙여도 이 예시는 그대로 남는다. 아직 다른 작품에서 재현을 못 봐서
  (`CLAUDE.md` 규칙 12 — 최소 2편 근거) 코드 버그로 승격은 안 했다.
- **LoRA(PEFT) 미시작.** 위 5번 표 참고. `corpus/pairs/`에 쌓는 중이고
  아직 학습 스크립트·평가 방법 자체가 없다 — 이건 데이터가 아니라 인프라가
  없는 상태다.
- **`--diarize`는 실전 검증 끝났고 정상 작동한다(2026-08-27).** 다만 검증
  과정에서 진짜 버그 하나를 더 찾아 고쳤다 — `merge_cues()`가 화자를
  비교할 때 `previous.end_ms`와 `event.start_ms`를 봤는데, 간격이 0인
  병합(whisper 조각이 딱 붙은 가장 흔한 경우)에서는 이 둘이 같은 시각이라
  비교가 항상 무의미했다. 각 조각 자체의 중간 지점을 비교하도록 고친 뒤
  실제로 병합 개수가 바뀌는 것을 확인했다(예능A 15회: 1103→1114).
  **교훈**: 유닛 시험은 통과했지만(간격 50ms로 짜서 이 사례를 못 잡았다)
  실전 데이터로 돌려 보고서야 드러났다 — 화자 정보처럼 실제 값의 분포가
  중요한 로직은 합성 시험만으로 부족할 수 있다.
- **화자 이름을 못 채운다(의도적 설계, 버그 아님).** 화자 분리는 "1번·2번
  화자가 다른 사람"까지만 안다. 실제 이름은 대본이 있어야 하고, 없으면
  사람이 영상을 보고 채운다 — 이름을 추측해서 채우지 않는다(규칙 3).
