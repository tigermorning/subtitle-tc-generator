# PRD — 자막 및 TC 생성기

이 문서는 다른 문서에 이미 있는 결정을 제품 요구사항 형태로 한곳에 모은 것이다.
새로운 결정을 이 문서에서 처음 만들지 않는다 — 근거가 바뀌면 원 출처를 먼저
고치고, 이 문서는 그것을 따라간다.

- 원 출처: `README.md`, `CLAUDE.md`(2026-11-08 재작성), 옛 작업 규칙 0~18번
  (`docs/RULES_ORIGINAL_HISTORY.md`로 옮겨짐), `docs/HANDOFF.md` 7절 «[우선 과제]»,
  `docs/SUBTITLE_EDITOR_PROJECT_BRIEF.md`(2026-08-11 결정 기록).
- **예외: 2026-11-11 사용자 결정.** 원 출처에 아직 없던 결정 셋(TC 정답 기준,
  자동 확정 비율 97%, 번역·SDH 1차 기준)을 이 문서와 `docs/HANDOFF.md` 7절에
  같은 날 함께 적었다. 출처는 «사용자 2026-11-11»로 단다.
- 마지막 확인: 2026-11-11.

## 문제

전문 번역가·자막 작업자는 영상 하나를 납품하기까지 TC(인점·아웃점) 작업 →
장면전환(SDH) → 전사 → 대조 → 번역 → 줄바꿈 → 글자 수·읽기 속도 교정을 거친다.
이 중 앞부분(초벌 만들기)은 시간이 많이 들지만 창의적 판단이 크게 필요하지 않은
반복 작업이고, 뒷부분(발주처 규정 준수, 300줄 중 놓친 것 찾기)은 사람이 하기엔
지루하고 실수하기 쉽다.

가장 큰 시간은 TC다. **대본이 주어졌을 때 인점·아웃점을 자동으로 확정**하는 것이
이 제품이 먼저 풀 문제다(`docs/HANDOFF.md` 7절, 사용자 2026-10-19 «TC는 100%
자동화되었으면 한다»). 자동 전사로 대사를 받아 적는 도구가 아니다.

## 대상 사용자

**맞춤법을 몰라서 이 도구를 쓰는 사람이 아니다.** 이미 숙련된 자막 작업자가,
반복 작업 시간을 줄이고 놓친 것을 잡기 위해 쓴다(README "최상위 목표").
나눠서 하던 TC·번역·SDH 작업을 한 사람이 맡고, 그 사람은 결과를 감수한다
(README "왜 한 사람이 통째로 맡게 만드는가").

## 목표 우선순위

```
자동 교정 오답 0  >  플래그 건수 감소  >  선택적 recall
```

**대상이 숙련자라서 이 순서다.** 틀린 자동 교정 하나는 사람이 못 알아채고
신뢰를 깨뜨리지만, recall을 조금 더 올려서 얻는 이득은 그 손해를 못 덮는다.
recall 100%는 사전 커버리지가 상한이라 원리적으로 불가능하므로 도달 목표로
세우지 않는다(README). 아래 "핵심 설계 원칙"은 대부분 이 순서 하나에서
갈라져 나온다 — 예: 위치 이동(`checker/position.py`)은 근거가 확실할 때만
자동 적용하고, 확신 없는 신호(`detect_bottom_text` 등)는 표시만 하고 고치지
않는다.

## 처리 순서 — 사용자 설계 (서비스 기준)

출처: `docs/HANDOFF.md` 7절 «[우선 과제]»(2026-10-19 사용자 지정).

| 순서 | 단계 | 내용 |
|---|---|---|
| 1 | TC 작업 | 전사 없이 파형·말소리 구간으로 인점·아웃점을 잡는다 |
| 2 | 장면전환 | TC 작업 뒤. SDH 작업만 한다(번역 작업은 건너뜀) |
| 3 | TC 자동 확정·잠금 | 사람 관문 없이 자동으로 확정한다. 이후 TC는 절대 움직이지 않는다 |
| 4 | 자막 작업 | 전사 → 대조(대본) → 번역(번역 작업만) → 줄바꿈(한 자막을 두 줄로) → 검사·교정 |

- 설계의 «재분할»은 줄바꿈(`checker/korean_break.py`)이다. TC를 바꾸는
  코드의 `resplit`(`checker/resplit.py`)은 설계에서 뺐다(HANDOFF 7절).
- **현재 코드는 이 순서와 다르다.** 코드는 전사 → 대조 → regroup → `resplit`
  → 장면전환(SDH) → 스포팅 순이고, 전사로 얻은 구간 시간이 TC의 재료다
  (HANDOFF 7절, `checker/generate.py` 호출 순서). `README.md` "작업 단계",
  `CLAUDE.md` 3절, `docs/HANDOFF.md` 2절은 코드 쪽 순서를 적고 있다.
- **결정(사용자 2026-11-11): 코드를 설계에 맞춘다.** 위 순서가 기준이고 코드가 따라온다. 어떻게 바꿀지(바꿀 곳·순서)는 `docs/HANDOFF.md` 7절의 «다음 사람이 할 일» 1·2번을 코드로 확인한 뒤 정한다.
  정해지기 전에는 코드도 위 문서들의 본문도 바꾸지 않는다.

### 설계를 코드로 옮길 때의 결정 (사용자 2026-11-11)

코드 조사(읽기 전용, 2026-11-11)에서 나온 걸림돌에 대한 답이다.

- **자막을 끊는 자리:** 인점·아웃점은 **전사·의미 파악 없이 사람 음성이 나오는 자리만, 음성 파형을 기준으로** 잡는다(사용자 2026-11-12). 절차는 `.claude/skills/TC-파형-인아웃/SKILL.md`.
- **확정 뒤 글이 칸보다 길 때:** TC는 그대로 두고 **글을 줄인다.** 지금 `converge`가 글자 수를 보고 아웃점을 늘리는 부분(`checker/timing.py` 162~173행)은 확정 뒤에는 쓰지 않는다.
- **자동 확정 판정:** 자막마다 확신도를 내는 장치가 생기기 전까지는 **정답이 있는 «처음 보는» 영상에서 잰 점수**로 정한다 — 그 방식이 97%를 넘으면 자동 확정으로 쓰고, 넘기 전에는 사람이 본다.
- **허용 오차:** «0.04초 미만»과 «정답과 같은 프레임» 중 무엇인지는 아직 미정이다(23.976fps에서 1프레임 = 41.7ms라 둘이 다르다). 정해질 때까지 채점은 둘 다 낸다.

## TC 정답 기준과 자동 확정 기준

- **정답 기준(사용자 2026-11-11):** TC의 정답은 이미 있는 인점·아웃점 작업
  규칙이다. 근거는 비공개 규정 자료 se-guide(`rules/private/se-guide/`)의 인점·
  아웃점 기준, 음성이 겹칠 때 다음 말소리 인점 우선, 장면전환 규칙이다. 같은
  인점·아웃점 여유는 세 발주처 `common.yaml`의 `spotting` 절에 들어가 있고
  (2026-10-16, 비공개 규정 저장소 커밋 `ac89a25`), 코드는 그 값을 읽는다
  (`0310fb8`, `checker/timing.py`).
- **자동 확정 기준:** 경계 하나의 오차가 **0.04초 미만**(HANDOFF 7절,
  사용자 2026-10-19)이고, 그 기준 안에 드는 자막이 **전체 자막의 97%**
  (분모는 전체 자막, 사용자 2026-11-11) 이상일 때 확정한다.
- **확인 필요:** 사용자는 2026-11-11에 같은 기준을 «정답과 같은 프레임»이라고도
  표현했다. «0.04초 미만»과 «같은 프레임»이 같은 기준인지는 사용자 확인이 필요하다.
- **아직 없는 것:** 실전에는 정답이 없으므로 도구가 스스로 «이 경계는 기준 안이다»라고
  판정할 신호(확신도)가 없다(HANDOFF 7절). 최신 코드의 TC 수치도 측정하지 않았다 —
  2026-09-13 수치는 그 뒤 개선이 반영되지 않은 옛 값이다(HANDOFF 7절).

## 번역·SDH 1차 결과 기준 (사용자 2026-11-11)

번역·SDH는 정답을 정하지 않는다. 1차 작업이라 사람 감수를 무조건 거친다.
1차 결과가 갖출 것은 셋이다.

1. 문맥에 맞고 오역이 없는 번역.
2. 대본에 나온 효과음이 SDH에 제대로 들어갔는가.
3. SDH에서 지양하는 표현을 피했는가.

규정·예시는 이미 프로그램 자료에 있다(비공개 규정 저장소의 발주처 프로파일과
`rules/private/sources/작업자-자료/`, `rules/lexicon/`).

## 범위 밖 선언

- **자막 편집기가 아니다.** 2026-08-12에 범위를 좁혔다 — SubtitleEdit(SE)을
  대체하거나 흉내 내는 기능은 만들지 않는다. 세부 손질은 작업자가 이미 쓰던 SE에서
  이어서 한다(`docs/SUBTITLE_EDITOR_PROJECT_BRIEF.md`가 이 전환의 기록이다).
- **한국어 맞춤법 규범 자체는 이 저장소가 아니다.** 판정 기준: "이 규칙을 이메일
  원고에 적용해도 말이 되는가" — 되면
  [korean-subtitle-corrector](https://github.com/tigermorning/korean-subtitle-corrector)(AI를
  쓰지 않는 규칙+국립국어원 API 엔진)의 몫이고, 안 되면(자막 고유의 형식·타이밍
  문제) 여기 몫이다.
- **클라우드 서비스에 원고를 보내지 않는다.** 방영 전 영상·대본은 유출되면 계약이
  깨지는 자료다. 전사는 로컬 whisper(faster-whisper 우선, 없으면 ffmpeg 내장),
  번역은 로컬 Ollama로만 한다.

## 핵심 설계 원칙 (옛 작업 규칙 요약 — 전체는 `docs/RULES_ORIGINAL_HISTORY.md`)

(로컬 전용은 여기 없다 — 품질이 아니라 기밀성 축이라 "범위 밖 선언"에만 둔다.)

| 원칙 | 요지 |
|---|---|
| 단계 순서 고정 | 전사(자유롭게) → 대조 → 번역 → 재분할 → 글자 수(마지막). 글자 수를 앞에서 맞추면 문장이 부서진 채 굳는다. **위 «처리 순서 — 사용자 설계»와 다르다 — 어느 쪽에 맞출지 결정 대기** |
| 원어 ≠ 한국어 규정 대상 | 원어 스크립트는 작업 재료일 뿐 납품물이 아니다. 글자 수·CPS 규정은 한국어 기준만 |
| 어느 쪽도 정답으로 두지 않는다 | 전사와 스크립트가 어긋나면 표시만 한다 |
| 확실한 근거 ↔ 추정 구분 | 파일 안에서 확인되는 것만 자동 교정, 영상에서 추정한 것은 알리기만 |
| 규정은 절대 기준, 버전은 수시로 바뀐다 | 공식 문건(`official: true`)과 발주처 실무 자료(`client`)를 구분하고, 발주처가 상속·override 가능. 넷플릭스·디즈니+·쿠팡플레이는 사용자가 준 실무 자료도 공식 규정으로 간주한다(2026-08-26·28 사용자 지시). 개정되면 어제 맞던 답이 오늘 틀린다 — 최신 버전인지 항상 재확인 |
| 학습이 규정을 침범하지 않는다 | 코퍼스에서 관측한 값(`rules/learned/`)은 위 공식 규정 파일을 절대 고치지 못한다 — 관측이 공식 문건과 갈리면 지적일 뿐 승격이 아니다. 규정으로 승격하는 유일한 길은 사람 확인 |
| 원본 불변 | 결과는 항상 새 파일로 낸다. 받은 타임코드는 검사·교정 경로에서 함부로 옮기지 않는다 — 되돌릴 수 있어야 자동 교정의 오답도 되돌릴 수 있다 |

## 성공 기준

**지금**: 전문가가 실제로 신뢰하고 쓰는가. 정량 지표(자동 교정 오답 0건, 미구현
검사 투명 공개, 정답 파일과의 구조적 대조 — `--against`)는 이 질문에 답하기
위한 수단이지 그 자체가 목적이 아니다.

**TC**: 위 자동 확정 기준(0.04초 미만, 전체 자막의 97%)을 넘는 것. 넘는지 재려면
먼저 최신 코드의 TC 수치를 다시 재야 한다(HANDOFF 7절 «다음 사람이 할 일» 5번).

**궁극적으로**: 정답지 없는 실전에서도 전문가가 감수만 하면 되는 수준으로
스스로 초안을 만드는 것. 정답지 학습(`rules/learned/`)이 이 목표로 가는
유일한 훈련 수단이다 — 오늘의 신뢰(위 "지금")는 그 여정의 중간 지점이지
종착점이 아니다.

자세한 현재 상태는 [`MVP.md`](MVP.md)를, 남은 일은 [`BACKLOG.md`](BACKLOG.md)와
`docs/HANDOFF.md` 7절을, 문서 지도는 [`README.md`](README.md)를 본다.
