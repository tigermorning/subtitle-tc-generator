# 정답지 대조 진단

`CLAUDE.md` 규칙 13을 코드화한 것이다. **정답지가 있는 것은 드문 기회다** — 실전
작업에는 정답이 없다. 이 진단의 목적은 "내 판단력을 연습"하는 게 아니라,
**정답 없는 실전에서도 통하는 도구 자체를 검증하고 고치는 것**이다.

## 언제 쓰나

- `정답지-학습` 스킬로 정답 srt를 확정한 영상이 아직 삭제되지 않았을 때
- **영상을 `학습완료`에서 지우기 전에 반드시 먼저 돈다** — 영상(음성)이 없으면
  전사를 다시 못 하므로 이 진단은 다시 할 수 없다. 이미 늦은 사례: 드라마A
  Texas, 예능B, 영화A, 드라마C(영상이 이미 삭제됨).

## 0. 시작 전에 — 이미 찾은 버그인지부터 확인한다

**전사·스윕부터 손대지 않는다.** 2026-08-29에 예능A 15회에서 "화자 바뀌어도
계속 이어붙인다"는 증상을 처음부터 다시 진단하고, whisper 전사까지 두 번(15·16회)
다시 돌려 gap/duration 스윕을 짠 뒤에야 `rules/genre/variety.yaml`에 **2026-08-27에
같은 증상·같은 근거(예능A 15회)로 이미 고쳐져 있던 값**(`merge_max_ms: 2000`)을
발견했다. 초안이 `--genre variety` 없이 생성돼 있어서 이미 있는 고침이 적용 안 된
것뿐이었는데, 그걸 "안 고쳐진 버그"로 오판하고 처음부터 다시 판 것이다 — 통째로
헛수고였다.

**그래서 증상을 확인하면 코드를 보기 전에 먼저 이 순서로 찾는다** (전사 재실행처럼
비용 큰 작업 전에 반드시):

1. `docs/HANDOFF.md`의 "6. 그동안 찾아 고친 구조적 버그" 절 — 증상과 겹치는
   항목이 있는지
2. `rules/genre/*.yaml`, `rules/learned/**/*.yaml`, `rules/<platform>/**/*.yaml`에
   같은 값(`merge_max_ms`, `merge_max_gap_ms` 등 증상과 관련된 키)을 grep
3. 겹치는 게 있으면: **그 값이 실제로 적용됐는지부터 확인**한다(생성 명령에
   해당 플래그 — `--genre`, `--profile` 등 — 가 빠지지 않았는지). 코드가 아니라
   생성 명령이 문제였을 가능성을 먼저 배제한다.
4. 위 셋을 확인한 뒤에도 증상이 안 풀리면 그때 아래 1~5번 절차(재전사·스윕·코드
   수정)로 넘어간다.

**대조 대상은 항상 "오늘 생성한 것 vs 정답지"다.** 과거 버전·어제 만든 결과·
"플래그 켰을 때 vs 껐을 때" 같은 자체 비교(ablation)를 설계하지 않는다(사용자
지적, 2026-08-30 — CLAUDE.md 규칙 13 참고). 다듬은 횟수처럼 다른 변수가 섞여서
시간만 먹고 원인을 못 가른다. 오늘 만든 결과를 정답지와 바로 대조해서 어긋난
자리를 보고 코드를 고친다 — "이게 저것보다 나은가"가 아니라 "정답과 어디가
다른가"만 묻는다.

## 절차

### 1. 초안을 만든다 (정답지는 보지 않는다)

```bash
python -m checker --generate --video <영상> --whisper-lang <ko|en|...> \
  -p <platform> -l <lang> -k <sdh|translation> -o <초안.srt>
```

- 번역이 필요 없는 SDH(원어=자막 언어)면 `--translate` 없이 돌린다 — 더 단순하고
  빠르다.
- 공식 프로파일이 없는 발주처(예: amazon)는 구조가 비슷한 공식 프로파일(예:
  netflix)을 임시로 써도 된다 — 이 진단의 목적은 규정 준수가 아니라 생성기 자체의
  스포팅·분할 로직 검증이다.

### 2. 정답과 대조한다

```bash
python -m checker <초안.srt> --against <정답.srt> --eval-json <out.json>
```

인점·아웃점 편향(가운데값·흩어짐·최악), 짝지음/빠뜨림/군더더기 개수, "가장 많이
어긋난 자막"(타이밍 기준)과 "텍스트가 가장 안 맞는 자막"(정답과 텍스트 유사도
기준) 개별 목록을 본다. **판정이 아니라 참고 신호다**(규칙 3·5) — 유사도가
낮다고 그 자체로 코드를 고치지 않는다. 아래 3번(개별 오차와 구조적 편향 구분)을
거쳐 여러 작품에서 같은 방향으로 반복되는 것만 코드 버그 후보로 본다.

번역 품질을 코퍼스 단일 점수(BLEU·ROUGE 같은)로 뭉뚱그리는 방법은 시도했다가
걷어냈다 — 실측해 보니 ROUGE-L은 이미 있던 텍스트 유사도와 값이 완전히
같았고, BLEU는 한국어 자막 특유의 짧은 어절 때문에 자주 0으로 무너져 정보량이
낮았다. 무엇보다 가운데값 하나로는 "어느 자막을 봐야 하는지"를 못 짚어 이
스킬의 목적(도구를 고치는 것, 규칙 13)에 안 맞았다. 그래서 지금은 개별 자막마다
텍스트 유사도를 재서 가장 안 맞는 것부터 보여 주는 방식을 쓴다. 지표 자체의
개념·함정(BLEU·ROUGE·perplexity·LLM-as-judge)은 `번역-품질-지표` 스킬을 본다.

### 3. 개별 오차와 구조적 편향을 구분한다

**TC(재분할·스포팅)를 먼저 본다 — 텍스트는 그다음이다**(CLAUDE.md 규칙 15,
2026-08-27). 자막 단위 자체가 정답과 안 맞으면(정답은 화자 턴마다 끊는데
우리는 이어 붙이는 등) 그 상태로 번역·표현을 손보는 건 헛일이다 — TC를
나중에 고치면 경계가 다시 생겨 텍스트 교정도 다시 해야 한다. 실측(예능A
15회 영어 번역 1453개 전수): 텍스트가 안 맞아 보인 자리의 상당수가 사실
`regroup.py`가 화자 교체를 못 보고 이어 붙인 TC 문제였다. 순서:

1. 정답이 한 화면에 담는 분량·화자 턴 경계와 우리 초안의 재분할 단위부터
   맞춰 본다. 구조적으로 어긋나면 `regroup.py`·`resplit.py`·`timing.py`부터
   고친다.
2. TC가 맞아떨어진 뒤에 번역·SDH 표현(어휘·고유명사·문체) 손교정으로 넘어간다.

- **한 편에서만, 몇 개만 어긋나는 것**은 노이즈다 — 코드를 고치지 않는다.
- **여러 회차·여러 작품·여러 장르에서 같은 방향으로 반복되는 것**만 코드 버그
  후보다. 최소 2편 이상에서 같은 패턴을 확인하고 고친다(규칙 12의 "몇 편 몇 개"
  증거 기준과 같은 정신).
- 의심 가는 자리를 직접 원문(정답 srt)과 초안에서 같은 시간대를 찾아 대조해
  본다 — duration이 `833/2000/4000/7000ms`처럼 딱 떨어지면 실제 스포팅 값이
  아니라 **어딘가의 상한·하한에 부딪혀 멈춘 값**이라는 신호다
  (`checker/timing.py`의 `converge()` max_duration_ms 클립처럼).

### 4. TC 손교정 — "가장 어긋난 자막" 목록을 그대로 믿지 않는다

`--eval-json`의 `pairs` 목록은 **시간이 가장 가까운 것끼리 기계적으로 짝지은
것**이다. 우리가 정답보다 자막 개수가 적거나 캡션을 못 만들면, 전혀 다른
대사끼리 억지로 짝지어져 인점·아웃점 편향이 수백~수천ms로 부풀려 보인다
(2026-08-27 실측: `DISTRIBUTED BY NETFLIX`라는 캡션이 `-Hello?`라는 실제
대사와 짝지어진 사례). **이 가짜 짝을 걸러야 진짜 TC 오차가 보인다:**

1. 정답 텍스트가 화면 캡션이면(대문자·숫자·문장부호로만 이루어짐) 애초에
   우리가 못 만드는 것이므로 짝에서 뺀다.
2. 남은 것 중 `similarity`(텍스트 유사도)가 낮으면(대략 0.5 미만) 다른 대사가
   시간만 가까워서 짝지어진 것으로 의심한다.
3. 아주 짧고 흔한 말("Yes.", "Hello.", "What?")은 유사도가 1.00이어도 같은
   대사가 여러 번 나오면 엉뚱한 자리끼리 짝지어질 수 있다 — 정답 텍스트 길이가
   짧으면(대략 20자 미만) 의심을 거두지 않는다.
4. 이렇게 거른 **진짜 짝**만 다시 인점·아웃점 편향의 중앙값을 재 본다 —
   실측(예능A 15회): 전체 통계는 편향 수백ms로 보였지만, 진짜 짝만 추리니
   중앙값이 130ms대(거의 프레임 단위)로 떨어졌다. 즉 원래 통계의 상당수가
   착시였다.
5. 그래도 남는 이상치(진짜 짝인데 편향이 큰 것, 대략 1500ms 초과)만 정답의
   타임코드로 하나씩 맞춰 고친다. **정답지 자체는 건드리지 않는다** — 우리
   초안의 해당 큐만 정답 타임코드로 갈아 끼운다.
6. 이상치가 특정 상황(웃음소리·박수 등 배경음이 이어지는 자리)에 몰리면
   그건 다시 코드 버그 후보다(3번으로 돌아간다) — 흩어져 있으면 건별 교정으로
   충분하다.

### 4. 코드를 고친다 (정답지·학습 자료는 절대 고치지 않는다)

- 고칠 대상은 `checker/`의 코드다. 정답지를 원인 규명 없이 재구성하거나, 학습
  자료(`rules/learned/`)에 이 결과를 섞지 않는다 — 이 진단은 별개 트랙이다.
- 고치고 나서 `tests/run_tests.py`로 회귀가 없는지 반드시 확인한다.
- **모든 편향이 코드로 완전히 고쳐지진 않는다.** 예: whisper가 노래·박수·비대사
  발성을 대사처럼 전사하는 문제(2026-08-26, 예능A·영화D·영화F
  세 작품에서 공통 확인)는 스포팅 코드 하나로 못 고친다 — 별도 기능(오디오가
  대사인지 아닌지 판별)이 필요한 규모면 `docs/BACKLOG.md`에 남기고 넘어간다.

### 5. 고침을 검증한다

같은 영상으로 다시 `--generate`+`--against`를 돌려, 지목했던 구체적인 사례
(타임스탬프 하나를 콕 짚어서)가 실제로 바뀌었는지 확인한다. **전체 평균이
좋아졌다고 성급히 말하지 않는다** — whisper 전사 자체가 GPU에서 매번 100% 같지
않고, 다른 원인(노래·효과음)이 더 크게 끼어 있으면 평균은 안 움직일 수 있다.
평균과 별개로, 고친 그 메커니즘이 실제로 고쳐졌는지를 개별 사례로 증명한다.
